# What v0.4 closes, and what is still open

As of 2026-11-20. v0.3 was reviewed for what it did well and where it fell short. This page is
that review, and the reason for each v0.4 change. The comparison with other tools is in
[compare.md](compare.md).

**In one line:** v0.3 was strong on state, proof, learning and cost. It was weak on finding out
what to build, on code review, on debugging method, and on running without stopping.

## What v0.3 already did well

| Strength | How |
|---|---|
| State | A deterministic CLI picks the task and owns the logs, the digest and `check`. No state lives in prompt wording. |
| Proof of "done" | `verify` re-runs the checks, compares the diff with the pack and catches weakened tests. |
| Learning | Gated lessons: screen, judge, owner approval, provenance, revoke. |
| Memory | A 150-line digest printed at session start; a fresh session starts where the last one stopped. |
| Cost | Hybrid mode: a free builder and a frontier judge. |
| Open choices | Scouts, isolated spikes, a judge comparison and a logged decision. |
| Evidence | A pre-registered 96-task trial with its failures published. |

## The gaps, and what v0.4 does about each

| Gap in v0.3 | v0.4 |
|---|---|
| No step for working out what to build: `shape` needed a finished plan, and nobody read that plan as a builder before tasks were cut from it. | `/dragonhoard:spec` writes the plan with the owner. `shape` has the judge read any plan as its builder first. |
| No code review: `verify` cannot tell whether the code does what the pack asked. | A `reviewer` role reads every task's diff against its pack. `checkpoint` commits only after verify and review passed. |
| Stale packs were found one task at a time, each costing a round-trip with the owner. | `dragonhoard.py lint` checks consumed files and tasks from the pack text, before a session is spent. |
| "Two failed attempts means BLOCKED", but no rule to find the root cause first. | A root cause is required before a second attempt, and `verify` fails a FAIL attempt without one. |
| It stopped after every task; solo mode could not run a milestone unattended. | `/dragonhoard:conduct` runs both modes, task after task, to the gate. |
| Two trial failures were still open: a rule-breaking owner request was obeyed, and an HTTP 402 was retried for hours. | Constitution article 18 turns such a request into a question. `delegate` stops at once with OUT-OF-CREDIT. |
| Skill text was untested. | `test_skills` fails when a skill names a command or an event kind the CLI does not have. |

Each fix follows the same rule: what can be a deterministic check lives in the CLI, where it
costs no tokens and cannot drift. The skills carry only the reasoning.

## Still open

- **Lesson effect size.** The lessons-on against lessons-off trial is designed in
  [evals/lessons-ab](../evals/lessons-ab/scorecard.md) and has not run.
- **v0.4 itself is not yet trialled.** The kart-racer trial audited v0.2. The reviewer, the
  solo run mode and `spec` have unit tests for their CLI parts, and no reliability trial yet.
- **Pressure tests.** Nothing tests a skill against an agent that tries to rationalise its way
  out of a rule. The tests only check that skills and CLI agree.
- **Self-diagnosis.** There is no skill that reads `logs/sessions/` and `events.jsonl` to explain
  a bad run.
- **Hosts.** Five are supported. The solo run mode needs Claude Code.
- **Branch finish.** `checkpoint` commits; merging and pull requests stay with the owner.
